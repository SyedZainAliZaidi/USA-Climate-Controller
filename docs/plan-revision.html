Two things the key disproved

Failure is silent — Completed does not mean you got data

read this one twice

The single most dangerous behaviour in this API. Everything below is a consequence of it.

A heatmap request for an area or a time the API has no data for is not rejected. It returns 200, it is assigned an activity_id, it polls through to status: "Completed", and it hands back an empty FeatureCollection. Nothing anywhere in the response says “no data”. The only tell is the shape of stats_data: 

// data present
"stats_data": { "temperature_stats": {...}, "overall_temperature_distribution": [...], ... }

// NO DATA — same 200, same "Completed"
"stats_data": { "activity_id": "...", "n_cells": 0 }
"map_data":   { "type": "FeatureCollection", "features": [] }

Built naively, the dashboard shows a blank map with a green last-updated timestamp and no error in any log. Assert on map_data.features.length > 0 before caching or rendering anything — treat an empty result as a failure, not a success. This cost the first verification run a false pass on every check; the harness now fails on zero tiles.

The forecast returns nothing — “predictive” has to be re-grounded

confirmed live

The 12-hour horizon is documented, and future timestamps are accepted at submit. They come back empty. So does everything in the last ~40 hours: 

now - 48h  (08-26 05:00Z)   tiles=74   mean=32.9 degC
now - 36h  (08-26 17:00Z)   tiles=0    EMPTY
now - 24h                   tiles=0    EMPTY
now -  3h                   tiles=0    EMPTY
now +  3h / +6h / +11h      tiles=0    EMPTY   // the "forecast"

The dataset ends at 26 Aug 13:00Z and lags real time by roughly 40 hours. There is no live reading and no forward projection to be had. Two consequences, neither fatal:

  • The demo runs on a fixed date. Pin it to 26 Aug 2026 and say so plainly on screen. The plan already committed to fixtures and to labelling stale data honestly — this is that policy, applied harder.
  • “When it peaks” comes from time_of_measure, not a forecast. It returns the peak hour per tile over a chosen day and it works: {"tile_id":0,"value":15} — peak at 15:00 UTC. That is the panel line the demo story needs, sourced from real data rather than a projection that does not exist.

Describe the system as heat-risk assessment with within-day peak prediction. Claiming a live 12-hour forecast in front of judges who know this API is a risk not worth taking.

Section 05, corrections

Four things to fix before Essam builds against the contract

The contracts are frozen, which is right — but four details in them will not survive contact with the API or with the demo. Cheaper to fix now than at integration.

1 · The AOI needs a FeatureCollection wrapper

will 400

The polygon in section 02 is a bare Polygon. The API requires the full wrapper:

"polygon_aoi": {
  "type": "FeatureCollection",
  "features": [{
    "type": "Feature",
    "properties": {},
    "geometry": {
      "type": "Polygon",
      "coordinates": [[ /* lon, lat — closed ring */ ]]
    }
  }]
}

Handled by featureCollection() in src/fg/client.js — pass a bare ring, get a valid payload.

2 · centroid and coordinates disagree on axis order

silent bug

The AOI ring is longitude-first (correct GeoJSON). The dashboard contract's "centroid": [24.4297, 54.6168] is latitude-first. Both are “right” by some convention, which is exactly why this kind of mismatch survives review and then puts a zone in the wrong hemisphere. Pick one and write it into the field name — centroid_lat_lon ends the argument permanently.

3 · The worked example does not match the contract, and proves nothing either way

two problems

Section 04 computes 51.4 + 2 + 3 + 0 − 0 = 56.4. The section 05 contract for the same zone says "risk_score": 53.4 — which is 51.4 + 2, the worker penalty dropped, even though drivers lists "outdoor workers present". One of the two is wrong.

The deeper problem: a heat index of 51.4 °C is already Extreme before a single contextual point is added. The demo's centrepiece zone therefore demonstrates nothing about the contextual engine — the clock alone would produce the same answer. Pick a worked example where context does the work: 

// Z-02, 13:40 — context moves the level
heat_index      49.0   -> Danger on its own
+ peak_hour     +2.0
+ worker        +3.0
= risk_score    54.0   -> Extreme

Now the zone is Extreme because workers are present at peak hour. That is the story the demo is built to tell.

4 · The timestamps are in the wrong timezone for the story

demo-breaking

The demo is a foreman at 13:40 local, at the hottest part of the day. The contract stamps that as "2026-08-28T13:40:00Z" — but in Phoenix (UTC−7) 13:40 local is 20:40Z, and 13:40Z is 06:40 in the morning. The "forecast_peak_time": "…T15:00:00Z" lands at 08:00 local, which is not a heat peak anywhere.

Store UTC, render local, and put the offset in the payload so the dashboard cannot get it wrong. /v1/env_params hands you metadata.timezone and metadata.timezone_offset_hours — use them rather than hardcoding. Note that time_of_measure returns its peak hour in UTC, so it needs the same treatment.

Section 04, one simplification

FortyGuard computes the heat index for you

Stage one gets shorter, and better sourced

confirmed

Stage one plans to compute the heat index from temperature and humidity using the NWS regression. /v1/env_params returns heat_index_celsius directly — so the value comes from the same API as the temperature, with no second source to explain and no regression to defend.

Our plan allows three parameters per request. Take heat_index_celsius, relative_humidity_percent and wet_bulb_temperature_celsius. The third is worth the slot: wet-bulb temperature is the measure occupational heat-stress standards are actually written against, and having it on the evidence slide is a stronger answer to “why these thresholds” than a citation alone.

The five bands themselves are sound — 27 / 32 / 39 / 51 °C are the NWS heat-index categories converted from 80 / 90 / 103 / 125 °F. Keep them, and cite the conversion.
